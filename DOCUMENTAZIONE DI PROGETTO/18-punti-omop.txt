Ho esplorato la documentazione OMOP/OHDSI partendo dal sito che hai indicato e seguendo i componenti tecnici collegati. Ne emerge una cosa interessante: **gran parte del motore che ci serve esiste già come insieme di librerie e specifiche**, ma è frammentato in progetti diversi. Il valore del nostro software potrebbe essere proprio unirli dietro un'architettura moderna, API coerenti e pipeline automatizzate.

## 1. La scelta fondamentale: OMOP CDM 5.5

Il sito OHDSI indica attualmente **OMOP CDM 5.5 come versione corrente**. La 6.0 esiste, ma OHDSI avverte esplicitamente che non è pienamente supportata dalla suite di strumenti; il cambiamento più problematico riguarda l'obbligatorietà dei `*_datetime`. 

Per il nostro progetto userei quindi:

**storage nativo OMOP CDM 5.5**, mantenendo compatibilità con il sottoinsieme 5.4 usato dagli strumenti OHDSI.

Questa soluzione è particolarmente ragionevole perché il passaggio 5.4 → 5.5 aggiunge 7 campi e 3 tabelle, ma **non elimina né rinomina alcuna tabella o campo**. 

Il caveat è che sul sito OHDSI diversi strumenti risultano compatibili con le funzionalità legacy della 5.5, ma non ancora pienamente con tutte le nuove feature della 5.5.

# 4. Il cuore semantico non è lo schema: sono i Concept

Qui sta probabilmente la parte più importante dell'intero progetto.

Un record OMOP tende ad avere tre rappresentazioni:

```text
condition_source_value
       ↓
condition_source_concept_id
       ↓
condition_concept_id
```

Per esempio:

```text
codice locale / ICD
        ↓
Source Concept
        ↓ "Maps to"
SNOMED Standard Concept
```

I campi `*_CONCEPT_ID` sono quelli su cui devono lavorare le analisi standardizzate; `*_SOURCE_VALUE` serve soprattutto per conservare il valore originale e per QA. 

Quindi il nostro **Vocabulary Service** dovrebbe essere un componente di prima classe, non una semplice tabella di lookup.

Dovrebbe fornire:

```text
searchConcept()
getConcept()
getAncestors()
getDescendants()
mapSourceConcept()
resolveConceptSet()
getRelationships()
getSynonyms()
validateDomain()
```

Questo permetterebbe poi di chiedere:

> tutti i pazienti con una patologia discendente da "Diabetes mellitus"

senza conoscere migliaia di codici ICD/SNOMED.

# 5. Mapping dei dati locali

OHDSI prevede esplicitamente il problema dei codici proprietari degli ospedali.

Usagi aiuta a trovare il mapping:

```text
CODICE LOCALE
    ↓
similarity/search
    ↓
OMOP Concept
    ↓
revisione umana
    ↓
mapping approvato
``` 


Per i concetti realmente locali OMOP consente **Custom Concepts**, imponendo tra l'altro `concept_id > 2.000.000.000`; devono essere non-standard e vanno utilizzati come source concepts, continuando a mapparli dove possibile verso concetti standard. 

Questo è particolarmente utile per un prodotto rivolto agli ospedali italiani: codifiche locali LIS, RIS, procedure interne, reparti, esami proprietari ecc. possono essere conservati senza inquinare il semantic layer standard.

# 9. Un'idea particolarmente utile: trasformare la specifica OMOP in metadata

Nel repository CommonDataModel OHDSI spiega che **la sorgente vera della definizione del CDM non è il DDL**, ma i file CSV strutturati che descrivono tabelle e campi; da questi vengono generate documentazione, DDL e parte delle regole Data Quality Dashboard. 

Io sfrutterei esattamente questa impostazione.

Il nostro software potrebbe avere un:

```text
OMOP Schema Registry
```

contenente per ciascuna versione:

```text
table
field
datatype
required
primaryKey
foreignKey
foreignTable
foreignDomain
userGuidance
etlConvention
cdmVersion
```

Da qui possiamo generare automaticamente:

```text
DDL
migrations
ORM models
API schemas
validation rules
ETL validation
documentation
data dictionary
```

Questa potrebbe diventare una delle fondamenta più forti dell'Hyper Connector.

# 10. ETL: qui possiamo riutilizzare parecchio

WhiteRabbit analizza automaticamente sorgenti SQL/CSV producendo informazioni su:

```text
tables
columns
types
distinct values
frequency distributions
```

e Rabbit-in-a-Hat aiuta a progettare il mapping sorgente → OMOP. 

Però non costruirei il nuovo prodotto intorno alla loro GUI Java.

Ne riutilizzerei **concetti, formati e algoritmi** creando un nostro ETL Designer web:

```text
SOURCE

ADT.PAZIENTE.cod_sesso
              │
              ├─ transform
              ▼
OMOP.PERSON.gender_concept_id
              │
              └─ vocabulary map
```

Ogni mapping dovrebbe avere:

```text
source
target
transform
concept mapping
filter
default
quality rule
version
author
timestamp
lineage
```

Questo renderebbe l'ETL completamente versionabile e riproducibile.

# 11. FHIR → OMOP è già stato standardizzato

Questa è un'altra libreria/documentazione molto rilevante.

HL7 sta sviluppando un **FHIR to OMOP Implementation Guide** specificamente per trasformare dati FHIR in OMOP. Copre l'acquisizione da singole Resource, Bundle e Bulk Data, mapping dei coded fields e diversi pattern di trasformazione. 

Il guide attuale è costruito sulla 5.4, quindi nel nostro software introdurrei:

```text
FHIR Adapter
     ↓
Canonical ingestion model
     ↓
FHIR→OMOP mapper
     ↓
OMOP 5.5
```

evitando di accoppiare direttamente il parser FHIR allo schema fisico OMOP.

Questo ci permetterà in futuro di aggiungere:

```text
HL7 v2 → canonical → OMOP
FHIR → canonical → OMOP
CSV → canonical → OMOP
JDBC → canonical → OMOP
DICOM metadata → canonical → OMOP
```

senza duplicare la logica.

# 12. Data quality come elemento obbligatorio

Non considererei un'importazione "terminata" quando l'ETL finisce.

La pipeline dovrebbe essere:

```text
ETL
 ↓
Structural validation
 ↓
OMOP semantic validation
 ↓
Data Quality Dashboard
 ↓
Achilles profiling
 ↓
release dataset
```

DQD applica una serie parametrica di tipi di controllo che genera circa **4.000 controlli individuali** nelle versioni documentate, includendo conformità, completezza e plausibilità. 

Achilles invece calcola statistiche descrittive sull'intera istanza OMOP e salva i risultati in uno schema separato. 

Per noi diventerebbero due servizi diversi:

```text
Quality Service
Characterization Service
```

# 13. Il motore delle coorti è già praticamente pronto

Una coorte potrebbe essere memorizzata come JSON:

```json
{
  "entry": "diabetes",
  "age": "> 65",
  "observation": ">= 365 days",
  "exclude": "renal failure"
}
```

Circe trasforma la definizione strutturata in SQL OMOP.

CohortGenerator la esegue e materializza:

```text
cohort_definition_id
subject_id
cohort_start_date
cohort_end_date
```

CohortGenerator supporta anche statistiche di attrition, risultati e generazione incrementale. 

Quindi **non riscriverei un linguaggio delle coorti da zero**.

Creerei invece un nostro Cohort Service sopra Circe/CohortGenerator.

# 16. Privacy: bisogna pensarla già nell'ETL

La documentazione OMOP avverte specificamente che:

`person_id` non dovrebbe contenere MRN o identificativi reali;

`*_source_value` può accidentalmente contenere PII;

stringhe libere come `value_as_string`, `sig`, `NOTE` e `NOTE_NLP` sono particolarmente rischiose;

eventuali date shifting devono essere applicati coerentemente a **tutti gli eventi della stessa persona**, altrimenti si altera la sequenza temporale. 

Perciò metterei tra `raw` e `OMOP` un vero:

```text
Privacy / De-identification Pipeline

tokenization
pseudonymization
PII detection
free-text quarantine
date handling
source-value sanitization
audit
```

La documentazione OHDSI è però prevalentemente orientata al contesto statunitense; per un prodotto europeo andrebbe sovrapposto il nostro modello GDPR e di governance.

# 18. La base tecnologica che sceglierei

A questo punto vedo abbastanza chiaramente il nucleo del prodotto:

```text
                 HEALTH DATA PLATFORM

                     API Gateway
                         │
        ┌────────────────┼─────────────────┐
        │                │                 │
 Connector Engine   Vocabulary Engine   Query Engine
        │                │                 │
 FHIR / HL7 / DB      Athena/Usagi       Cohorts
        │                │              Features
        └────────┬───────┴──────────┬──────┘
                 │                  │
           ETL / Lineage         Analytics
                 │                  │
                 ▼                  ▼
             OMOP CDM 5.5 ───► Results
                 │
            ┌────┴────┐
            │         │
           DQD     Achilles
```

Per una prima implementazione concreta userei:

| Componente | Scelta |
|---|---|
| DB principale | **PostgreSQL** |
| OMOP | **CDM 5.5** |
| Raw storage | S3/MinIO + Parquet |
| ingestion | connector architecture |
| FHIR | HAPI FHIR / FHIR parser + HL7 FHIR→OMOP IG |
| HL7 v2 | HAPI HL7 / Mirth-compatible connector |
| ETL | nostro engine + SQL |
| Vocabulary | Athena + OMOP vocabulary |
| Mapping | Usagi-compatible |
| Cross-DB SQL | **SqlRender** |
| Quality | **DataQualityDashboard** |
| Profiling | **Achilles** |
| Cohorts | **Circe + CohortGenerator** |
| Features | **FeatureExtraction** |
| Analytics | **HADES** |
| OHDSI compatibility | WebAPI sidecar |
| UI OHDSI | ATLAS opzionale |
| API prodotto | nuova API REST |
| Identity | OIDC / Keycloak |
| deployment | Docker/Kubernetes |

Il punto importante è che **non stiamo progettando un database OMOP**. Stiamo progettando un **OMOP Data Platform / Healthcare Data Fabric**.

Il CDM diventa solamente il cuore standardizzato.

La parte che può avere maggior valore proprietario è invece:

```text
CONNECT
   ↓
UNDERSTAND
   ↓
MAP
   ↓
STANDARDIZE
   ↓
VALIDATE
   ↓
QUERY
   ↓
ANALYZE
```

e buona parte degli ultimi quattro livelli può essere costruita integrando codice OHDSI già esistente anziché reinventarlo.

La prossima mossa utile, a mio avviso, è trasformare tutto questo in una **vera architettura software del nostro Hyper Connector sanitario**, definendo repository/moduli, servizi, database/schema, API interne, container Docker e dipendenze OHDSI da incorporare o mantenere come sidecar. Questa ricerca ci dà già materiale sufficiente per impostarla in modo piuttosto concreto.
